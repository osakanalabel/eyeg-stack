# Check 重みづけアルゴリズム仕様（v1.1 ドラフト）

core.md「Checkの設計思想」に列挙された重みの構成要素を、計算可能な式として具体化する。

| 版 | 内容 |
|----|------|
| v1 | 6要素の重み付き線形和（加算型スコアリング） |
| v1.1 | S_cat（カテゴリ×時間帯）を**ファジィ化**。時間帯境界の不連続ジャンプを解消（他要素は v1 のまま） |

## 設計方針

- **AI/ML は使わない決定式**で実装する。
  - 推論コストゼロ・低レイテンシ（Check 表示のたびに計算しても無料・即時）
  - 説明可能（なぜこのメモが上に来たかを要素分解で示せる）
  - 決定性: 入力 (メモ, 現在時刻, タイムゾーン) が同じなら必ず同じ結果 → 時刻を固定してユニットテスト可能
- 個人化は既存の行動データ（手動順位操作・閲覧回数）で実現する。ML なしで「使い込むほど自分好みになる」を成立させる。
- 全定数はチューニング前提の設定値として一元管理する（コード中にマジックナンバーを散らさない）。
- 将来 AI を使いたくなった場合の差し込み口を1箇所だけ予約する（末尾参照）。
- **ファジィ理論の考え方を限定的に採用する（v1.1）**。各スコアの 0〜1 正規化はメンバーシップ関数（「期限が近い度合い」等）の発想であり、S_cat は時間帯のメンバーシップ関数＋0次 TSK（Takagi–Sugeno）合成で計算する。ルール推論全体（Mamdani 型）までは持ち込まない — 計算は依然すべて決定式・コストゼロのまま。参考: 北海道大学 河口万由香 准教授のファジィ論理研究（t-ノルム／ユニノルムの代数的構造、疎なファジィルールベースのルール補間。末尾「参考文献」参照）。

## 全体式

```
weight = 0.30·S_due + 0.20·S_imp + 0.15·S_cat + 0.15·S_fresh + 0.05·S_view + 0.15·S_man
```

| 要素 | 係数 | 値域 | 意味 |
|------|------|------|------|
| S_due | 0.30 | 0〜1 | 期限の近さ |
| S_imp | 0.20 | 0.2〜1 | 重要度 |
| S_cat | 0.15 | 0.2〜1 | カテゴリ×時間帯 |
| S_fresh | 0.15 | 0〜1 | 鮮度（新規・更新直後） |
| S_view | 0.05 | 0〜1 | 閲覧回数 |
| S_man | 0.15 | −1〜+1 | 手動順位操作（唯一の符号つき要素） |

正側係数の合計は 0.85、S_man 込みの理論最大はほぼ 1.0。weight は**相対順位にのみ**使い、絶対値自体に意味は持たせない。

## 各要素の定義

### S_due — 期限の近さ（係数 0.30）

- `due_at` なし → 0
- 期限は「**ユーザーのタイムゾーンにおける期限日の終わり（23:59:59）**」とみなす（UI が日付入力のため、時刻の規約をここで固定する）
- 残り日数 d（実数）に対して:
  - d ≤ 0（期限切れ）→ **1.0**
  - 0 < d ≤ 7 → **1 − d/7**（線形に上昇）
  - d > 7 → 0
- 注記: 期限切れは 1.0 を維持し続ける＝浮上し続ける（忘れさせないのが正）。ただし完了/アーカイブ機能が無い間は期限切れメモが上位に固定され続ける。**アーカイブ等のライフサイクル機能の導入が対の前提**。

### S_imp — 重要度（0.20）

- importance (1〜5) → **importance / 5**（0.2〜1.0）
- 未設定 (NULL) → **0.4**
  - 根拠: 明示的な「低い」(1 = 0.2) より上、「普通」(3 = 0.6) より下。未評価メモが評価済みメモに常に勝つ／常に負ける事態を避ける中立点。

### S_cat — カテゴリ×時間帯（0.15）【v1.1 でファジィ化】

時間帯判定はユーザーTZのローカル時刻・曜日で行う。**ルール表**（ファジィルールの後件部に相当）:

| 時間帯 | work | general | personal |
|--------|------|---------|----------|
| 平日昼（中心域 8:00〜18:00） | 1.0 | 0.6 | 0.3 |
| 平日夜（中心域 18:00〜翌8:00） | 0.4 | 0.6 | 1.0 |
| 週末（土日終日） | 0.2 | 0.7 | 1.0 |

**ファジィ合成（0次 TSK）**: 平日は時間帯を crisp に切り替えず、台形メンバーシップ関数 μ_昼 で度合いとして判定し、ルール表の値を加重平均する。

```
μ_昼(t) =  0                     （t < 7:30 または t ≥ 18:30）
           (t − 7:30) / 1h       （7:30 ≤ t < 8:30 … 立ち上がり）
           1                     （8:30 ≤ t < 17:30）
           (18:30 − t) / 1h      （17:30 ≤ t < 18:30 … 立ち下がり）

μ_夜(t) = 1 − μ_昼(t)            （相補的 → 合成重みは常に正規化済み）

S_cat = μ_昼 × 表[平日昼][cat] + μ_夜 × 表[平日夜][cat]   （平日）
S_cat = 表[週末][cat]                                      （土日）
```

- 境界 8:00 / 18:00 を中心に ±30分（`CAT_BLEND_MIN` = 60分幅）の遷移帯で線形にクロスフェードする。
- **狙い**: crisp 版では 17:59→18:00 の瞬間に work が 1.0→0.4 へ跳び、使用中に一覧が突然入れ替わって見える。ファジィ化により同じ変化が1時間かけて滑らかに起こる（検証値: work は 17:45 に 0.850、18:00 に 0.700、18:15 に 0.550、18:30 に 0.400）。
- 遷移帯の外では crisp 版と完全に一致する（後方互換。v1 の計算例はそのまま有効）。
- general はどの時間帯でも中位＝時間帯に左右されにくい受け皿。
- **v1.1 で残す簡略化**: 曜日種別（平日/週末）の切り替えは crisp のまま（日曜深夜→月曜 0:00 に work が 0.2→0.4 と小さく跳ぶが、weight への影響は 0.15×0.2 = 0.03 で許容）。祝日判定も初版では行わない（曜日のみ）。いずれも将来、日付側のメンバーシップ追加・祝日テーブルで同じ枠組みのまま拡張可能。
- **将来の深掘り（任意）**: 「期限が近い AND 重要」のような相乗ルールを積 t-ノルムで追加する、符号つき S_man の合成をユニノルムで定式化する、といった拡張は本枠組みと整合する。採用時は別途バージョンを上げる。

### S_fresh — 鮮度（0.15）

- 基準時刻 touched = max(created_at, updated_at)
- 経過 t 時間に対して: **S_fresh = 0.5^(t / 24)**（半減期24時間。3日後 ≈ 0.125、1週間後 ≈ 0.008）
- **実装規則（重要）**: view_count・manual カウント・last_viewed_at 等の**カウンタ更新では updated_at を更新しない**。updated_at が動くのは本文・属性の編集時のみ。これを破ると「見るたび新鮮に戻る」ループが生まれる。

### S_view — 閲覧回数（0.05）

- **S_view = min(1, log2(1 + view_count) / log2(1 + 100))**（100回で飽和）
- 正帰還ループ（見る→上がる→また見る→さらに上がる）への対策を3重にする:
  1. 対数で逓減（1→2回目の効果 ≫ 99→100回目の効果）
  2. 係数を全要素中最小（0.05）にする
  3. **加算規則**: 同一メモへの閲覧カウントは前回閲覧から**1時間以上**空いた場合のみ +1（API 側で last_viewed_at を見て判定）

### S_man — 手動順位操作（0.15・符号つき）

- net = manual_up_count − manual_down_count
- 強さ: **base = tanh(net / 5)** ∈ (−1, 1)。net = ±5 で約 ±0.76、±10 で約 ±0.96 と飽和（事実上の上限キャップ）
- 時間減衰: **decay = 0.5^(last_manual_at からの経過日数 / 21)**（半減期3週間）
- **S_man = base × decay**。操作履歴なし（last_manual_at が NULL）→ 0
- 設計意図: core.md の「あくまでアルゴリズムの結果がベース。手動操作はその上への意思の上書き」を式で表現したもの。手動操作は**位置の固定ではなく重みへの寄与**なので、ドロップした位置にそのまま収まるとは限らない。操作しなくなれば3週間単位で自然に薄れる。
- **操作規則（API 側）**: 1回のドラッグで加算できる段数は実際に移動可能な範囲（一覧の上端／下端まで）に**クランプ**する。現モック（check.html）は未クランプで、勢いよくドラッグすると過大な段数が加算されるため本実装で修正すること。

## 並び順の確定

1. weight 降順
2. 同値: created_at 降順
3. なお同値: id 昇順（完全な決定性の担保）

## 計算場所と決定性

- **サーバ側・クエリ時計算**（weight は保存しない）。1ユーザーのメモは高々数百〜数千想定なので都度計算で十分。SQL でも書けるが、テスト容易性からアプリ層の純関数を推奨。
- 純関数のシグネチャ: `weight(memo, ctx)`、ctx = { now, tz }。同入力なら同出力。
- クライアントは `GET /memos?view=recommended` に **IANA タイムゾーン**（例: `tz=Asia/Tokyo`）を渡す。サーバはこれで時間帯・期限日の終わりを解決する。

## 擬似コード

```
function weight(memo, ctx):
    s_due   = dueScore(memo.due_at, ctx)                 # 0..1（上記定義）
    s_imp   = memo.importance ? memo.importance / 5 : 0.4
    s_cat   = isWeekend(ctx) ? CAT_MATRIX[weekend][memo.category]
            : μ_day(ctx) × CAT_MATRIX[day][memo.category]
              + (1 − μ_day(ctx)) × CAT_MATRIX[night][memo.category]   # 0次TSK
    s_fresh = 0.5 ^ (hoursSince(max(memo.created_at, memo.updated_at)) / 24)
    s_view  = min(1, log2(1 + memo.view_count) / log2(101))
    s_man   = (memo.last_manual_at == null) ? 0
            : tanh((memo.manual_up_count − memo.manual_down_count) / 5)
              × 0.5 ^ (daysSince(memo.last_manual_at) / 21)
    return 0.30·s_due + 0.20·s_imp + 0.15·s_cat
         + 0.15·s_fresh + 0.05·s_view + 0.15·s_man
```

## 計算例（スクリプト検証済み）

check.html のダミーデータ6件、**2026-06-10（水）14:00 JST（平日昼）**時点:

| 順位 | メモ | S_due | S_imp | S_cat | S_fresh | S_view | weight |
|------|------|-------|-------|-------|---------|--------|--------|
| 1 | #5 チームに設計方針の共有（仕事・★5・今日期限） | 0.940 | 1.000 | 1.000 | 0.459 | 0.300 | **0.716** |
| 2 | #2 週次レポート金曜まで（仕事・★4・6/13期限） | 0.512 | 0.800 | 1.000 | 0.226 | 0.388 | **0.517** |
| 3 | #4 歯医者の予約（私用・★3・6/15期限） | 0.226 | 0.600 | 0.300 | 0.054 | 0.000 | **0.241** |
| 4 | #3 Next.js を調べる（一般・★2） | 0 | 0.400 | 0.600 | 0.153 | 0.150 | **0.200** |
| 5 | #1 牛乳と卵を買う（私用・無印・昨日作成） | 0 | 0.400 | 0.300 | 0.420 | 0.238 | **0.200** |
| 6 | #6 週末に読む本（一般・無印・5日前） | 0 | 0.400 | 0.600 | 0.036 | 0.349 | **0.193** |

※ #3 = 0.2004、#1 = 0.2000 でほぼ同値。S_man は全件 0 のため列を省略。

→ 平日昼は「今日期限・重要度5の仕事メモ」が確実にトップ。直感に合う並び。

**手動操作の効き方**: #6 を3段上げると S_man = tanh(3/5) = 0.537、寄与 +0.081 で weight 0.193 → 0.273 となり **6位 → 3位**に浮上。3週間後（他要素不変と仮定）には寄与が +0.040 に半減し、操作し続けなければ自然に沈む。

**時間帯境界の遷移（v1.1・スクリプト検証済み）**: 平日 18:00 前後の S_cat。crisp 版の瞬間ジャンプが1時間の線形遷移になる。

| 時刻 | work（crisp → fuzzy） | personal（crisp → fuzzy） |
|------|----------------------|---------------------------|
| 17:30 | 1.000 → 1.000 | 0.300 → 0.300 |
| 17:45 | 1.000 → 0.850 | 0.300 → 0.475 |
| 18:00 | 0.400 → 0.700 | 1.000 → 0.650 |
| 18:15 | 0.400 → 0.550 | 1.000 → 0.825 |
| 18:30 | 0.400 → 0.400 | 1.000 → 1.000 |

14:00 のような遷移帯の外では crisp と fuzzy は完全一致するため、上の6件の計算例は v1.1 でもそのまま成立する。

## 定数一覧（チューニング表）

| 定数 | 初期値 | 意味 |
|------|--------|------|
| W_DUE / W_IMP / W_CAT / W_FRESH / W_VIEW / W_MAN | 0.30 / 0.20 / 0.15 / 0.15 / 0.05 / 0.15 | 各要素の係数 |
| DUE_HORIZON_DAYS | 7 | 期限が効き始める残り日数 |
| IMP_UNSET | 0.4 | 重要度未設定時のスコア |
| FRESH_HALF_LIFE_H | 24 | 鮮度の半減期（時間） |
| VIEW_CAP | 100 | 閲覧スコアが飽和する回数 |
| VIEW_DEDUP_MIN | 60 | 閲覧カウント加算の最短間隔（分） |
| MAN_SCALE | 5 | 手動 net がほぼ飽和する段数 |
| MAN_HALF_LIFE_D | 21 | 手動効果の半減期（日） |
| CAT_BLEND_MIN | 60 | 時間帯境界の遷移帯の幅（分）。8:00 / 18:00 を中心に ±30分 |

初期値は上記計算例で妥当性を確認した出発点。実利用の体感に合わせて係数から調整する。

## 将来の AI 差し込み口（初版は実装しない）

```
score = weight(memo, ctx)          // 本仕様の決定式
score = rerank(score, memo, ctx)   // 差し込み口。初版は恒等関数（そのまま返す）
```

将来 AI を入れる場合もリアルタイム推論は避け、夜間バッチで算出した補正値をカラムに保持して rerank が読むだけ、といった低コストな形を推奨。本仕様の決定式は常にフォールバックとして残す。

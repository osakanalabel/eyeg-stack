# EyeG-Stack コアコンセプト

## プロダクトの本質

EyeG-Stackは「さっとメモして、あとで勝手に浮かび上がってくる」体験を作るスマホ向けWebアプリ。

Google Keepのような手軽さを持ちながら、見るときは重みづけによって重要なメモが自然に前面に出てくる。ユーザーは探さなくていい。必要なものが来る。


## EyeGシリーズの思想

**かんたん・シンプルであること**を最優先とする。

- 機能は役割ごとに分離する。
- 「便利だから」という理由で機能を混ぜない。シンプルさが損なわれることを嫌う。
- 迷わない・説明不要・すぐ使える、を常に意識する。


## Push と Check の役割 — effect / output

EyeG-Stack の機能は **Push** と **Check** の2系統に分ける。この分離は「入力 / 出力」ではなく **「effect（作用）/ output（出力）」** として捉える。

- **Push = effect** — メモの状態を**変える**操作。作成・編集・削除など、データに作用するものはすべて Push 側に置く。
- **Check = output** — メモを**読み取って見せる**閲覧。データを変えない。破壊的・変更系の操作は持たせない。

この区分けが、機能の置き場所に迷ったときの判断基準になる。

- 編集・削除は Check（閲覧）には置かず、Push 画面（編集モード）へ遷移して行う。
  シリーズ姉妹アプリ eyeg-cal も「閲覧側では削除せず、別画面へ遷移してから削除する」同じ作法を取っている。
- **例外** — Check の手動順位操作（`manual_up_count` / `manual_down_count` の加算）は、
  厳密にはカウントを変える effect だが、「より良く output するための並び調整」として Check 側に残す。
  これは output をユーザー好みに最適化する行為であり、データの新規作成・編集・削除とは性質が異なるため。


## なぜ作るか

Google KeepのAPIは非公開であり、外部から制御できない。EyeG-Stackは自前でAPIごと実装することで、重みづけロジックや他のEyeGシリーズとの連携を自由に設計できる。


## 操作の語彙

| 操作 | 名称 | 説明 |
|------|------|------|
| メモを追加する | **Push** | スタックに積む |
| メモを見る | **Check** | スタックを確認する |


## Pushで記録できること

- メモ日時
- メモ文
- 写真（最大4枚、長辺1024px程度に縮小して保存）
- GPS位置情報
- カテゴリ（私用 / 仕事用 / 一般）
- 重要度
- 期限


## Checkの設計思想

標準ビューはソートではなく**重みづけ**で表示順を決める。重要なメモが自然に浮上してくるUX。

### 重みの構成要素

- カテゴリ × 時間帯（日中は仕事優先、週末は私用優先、など）
- 重要度
- 期限の近さ
- メモの閲覧回数
- 鮮度（新規 / 更新直後）

### その他の閲覧方法

重みづけ以外のソート・フィルタも提供する。

- 日付順
- カテゴリ別
- その他（今後定義）


## 手動介入による重みのチューニング

Checkの標準ビューはアルゴリズムが計算した重みづけ順を基本とする。ただしユーザーは一覧上でメモを長押し→ドラッグして順位を手動で動かすことができる。

- 動かした分（例: 3つ上げたら +3）が `manual_up_count` / `manual_down_count` に加算される
- このカウントは重みづけの構成要素のひとつとして次回以降の順位計算に寄与する
- あくまでアルゴリズムの結果がベース。手動操作はその上への「意思の上書き」

使い込むほど自分好みにチューニングされていく体験を目指す。


## 将来構想

### Googleカレンダー連携
初版リリース時は対象外。将来的にはEyeG-Cal経由での連携を検討。

### EyeGシリーズとの関係
EyeG-Stackは独立したアプリだが、EyeGシリーズの一員として他サービスとの連携を前提に設計する。APIを自前実装するのはこのためでもある。


## デザイン方針

- EyeGシリーズとして外観・UIの統一感を持たせる
- テーマカラーはEyeG他アプリとは異なる独自のものを設定する（色は未定）


## 技術方針

- スマホ向けWebアプリ（ブラウザで動作）
- APIは自前実装
- 詳細なアーキテクチャは別途定義

## 認証方針

- 認証モジュールは他機能と疎結合に実装する。将来的にOAuthや2段階認証への差し替えを前提とする。
- 初期実装はID＋パスワード方式。パスワードは **Argon2** でハッシュ化して保存する（暫定）。
